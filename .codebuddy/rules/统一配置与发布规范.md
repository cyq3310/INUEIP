# 统一配置与发布规范（myconfig 单一配置源 + 生产可配置 + 发布检查）

## 适用范围

本规范约束 INUEIP 项目（`backend/` ThinkPHP 8 + PHP>=8.0，`frontend/` Vite + Vue3 + TS）的**配置来源、生产环境可配置项、以及每次「检查发布 / 上传 git」时 AI 必须执行的动作**。
凡涉及新增配置、修改配置、打包上线、提交代码的请求，一律先按本规范执行。

## 强制标准（默认遵循）

1. **单一配置源**：全平台可配置项只允许写在 `backend/config/myconfig.php`，禁止新增第二份配置文件，禁止在业务代码里写死环境相关内容。
2. **生产可配置**：IP、端口、域名、图片资源、skill 文件来源等必须可在 myconfig 中切换（`local` / `cdn` / 远程地址 三种来源），不得依赖本地是否存在某个文件。
3. **发布必检查**：每次被要求「检查发布 / 上传 git」时，必须输出发布检查清单；若 `myconfig.php` 有变更，必须单独成节并**先向用户确认能否上传**，未确认前不得提交或推送该文件。

## 一、myconfig 单一配置源约定

1. **唯一文件**：所有配置写在 `backend/config/myconfig.php`，返回 PHP 数组（`<?php return [...];`，UTF-8 无 BOM，文件内不得有任何输出）。ThinkPHP 8 会自动加载 `backend/config/` 下所有 php，代码内统一用 `config('myconfig.deploy.env')`、`config('myconfig.site.name')` 读取。
2. **禁止第二配置源**：不得新建 `config_extra.php`、`custom.php`、`settings.php`、`.env.production` 之外的散落配置文件；`backend/app/**` 业务代码中不得出现「可配置项」的常量、数组字面量或 `define()`。
3. **新增配置项写哪里**：凡是「换环境可能变」的东西——第三方/自身地址、端口、超时、分页条数、功能开关、图片前缀、上传限制、密钥有效期——一律写进 myconfig。只有与业务强耦合且不随环境变化的逻辑常量可留在业务代码，且必须在行尾注释写明「不随环境变化，故不进 myconfig」。
4. **分组结构（新增分组需同步更新本节清单）**：

   ```php
   return [
       // site：站点展示信息，页脚 / 关于页 / 后台标题使用（name、version、copyright、icp）
       'site' => ['name' => '', 'version' => '', 'copyright' => '', 'icp' => ''],

       // deploy：部署环境。env=local|staging|production；
       //   api：后端接口自身对外地址（scheme/host/port/base_url/timeout），用于回调、定时任务、生成绝对链接
       //   web：前端站点对外地址（scheme/host/port/base_url），用于分享链接、邮件链接、构建注入
       //   resource：静态资源来源，mode=local|cdn，base_url 为 CDN/远程根地址
       //   cors：跨域白名单，allow_origin 必须等于 web.base_url
       'deploy' => [
           'env' => 'production',
           'api' => ['scheme' => 'https', 'host' => '', 'port' => 443, 'base_url' => '', 'timeout' => 10],
           'web' => ['scheme' => 'https', 'host' => '', 'port' => 443, 'base_url' => ''],
           'resource' => ['mode' => 'local', 'base_url' => ''],
           'cors' => ['allow_origin' => ''],
       ],

       // database：与 backend/.env 中 DB_* 一致的真实连接参数（类型、主机、端口、库名、账号、密码、前缀、字符集）
       'database' => ['type' => 'mysql', 'hostname' => '', 'hostport' => 3306, 'database' => '', 'username' => '', 'password' => '', 'prefix' => 'inue_', 'charset' => 'utf8mb4'],

       // jwt：令牌密钥与有效期（秒）。secret 为私密项，禁止进日志与接口返回
       'jwt' => ['secret' => '', 'expire' => 7200],

       // upload：上传驱动、存储根目录、访问 URL 前缀、单文件上限（字节）、允许扩展名数组
       'upload' => ['driver' => 'local', 'root' => '', 'url_prefix' => '', 'max_size' => 0, 'allowed_ext' => []],

       // announcement：公告图片。upload_prefix 为本地上传访问前缀，remote_base_url 为 CDN/远程根地址
       'announcement' => ['upload_prefix' => '', 'remote_base_url' => ''],

       // portal_theme：门户背景图。字段含义同 announcement
       'portal_theme' => ['upload_prefix' => '', 'remote_base_url' => ''],

       // skill：skill 文件来源。source=local|remote|api；local_path 为本地相对路径，
       //   remote_base_url 为远程根地址，api_endpoint 为接口地址，use_mock=true 时返回内置 mock 数据
       'skill' => ['source' => 'local', 'local_path' => '', 'remote_base_url' => '', 'api_endpoint' => '', 'use_mock' => false],

       // portal：门户业务默认值，如默认分页条数、列表条数等
       'portal' => ['page_size' => 10],

       // frontend_public：可下发到前端的键白名单（一维数组，值为"分组.键"），前后端共用同一份配置
       'frontend_public' => ['keys' => ['site.name', 'site.version', 'site.copyright', 'site.icp', 'deploy.env', 'deploy.api.base_url', 'deploy.api.timeout', 'deploy.web.base_url', 'deploy.resource.mode', 'deploy.resource.base_url', 'skill.source', 'skill.use_mock', 'skill.local_path', 'skill.remote_base_url', 'portal.page_size']],
   ];
   ```

5. **命名规范**：分组名与键名一律小写下划线 `snake_case`；布尔开关用 `enable_` / `use_` 前缀；时间/超时用整数秒，后缀 `_timeout` / `_expire` / `_ttl`；地址类键以 `_url` 结尾，数组类以复数或 `keys` / `ext` 表达；层级最多三级（分组 → 子组 → 键）。
6. **注释要求**：每个分组上方写一行块注释说明用途；每个键行尾用 `//` 注明「用途 + 取值枚举 + 默认值」。存在枚举的键必须写全枚举值（如 `// local|staging|production`，`// local|cdn|remote`），便于换环境时直接改值。
7. **禁止硬编码地址**：后端不得拼接 `http://IP:端口` 字面量；前端 `frontend/src/api/request.ts` 的 `baseURL` 不得硬编码域名或端口（保留 `/api` 相对路径，或由 `deploy.api.base_url` 注入）。所有外部地址一律从 `config('myconfig....')` 取值。
8. **私密项红线**：`database`、`jwt` 两组写入真实生产值并入库（已确认接受），但必须做到：不进 `frontend_public.keys`、不进接口响应体、不进日志（日志中如必须打印连接信息只打主机与库名，密码与 secret 脱敏为 `***`）、不在错误信息中回显。
9. **与 `.env` 的关系**：`backend/.env` 仅保留框架级开关（如 `APP_DEBUG`）；`DB_*`、`JWT_SECRET`、`JWT_EXPIRE` 以 myconfig 为**权威源**，`.env` 保持同步即可（`.env` 已 gitignore，不入库）。若两者不一致，以 myconfig 为准，并在发布清单中提示「生产需同步 .env」。
10. **前端取配置的唯一入口**：后端提供免登录接口 `GET /api/config`，仅按 `frontend_public.keys` 白名单下发键值；前端不得从其它途径读取环境配置，也不得在前端代码里再写一份常量。新增需要下发前端的项，必须显式加入 `frontend_public.keys`，否则接口不下发。
11. **改配置的流程**：改键 → 同步更新注释与枚举 → 判断是否需加入 `frontend_public.keys` → 本地验证 `config('myconfig.xxx')` 取值正确且 `GET /api/config` 返回符合预期 → 按第四部分走发布检查（myconfig 变更必须先经用户确认）。
12. **`GET /api/config` 接口约束**：该接口为免登录接口，路由必须写在 `backend/route/app.php` 中 `Route::group('api', ...)->middleware(AuthCheck::class)` **之外**（与 `Route::post('api/auth/login', 'Auth/login')` 同级）；控制器只允许按 `frontend_public.keys` 逐个取值后 `resp_ok()` 返回，禁止整包返回 myconfig、禁止返回 `database` / `jwt` 任何键；可加短期缓存，但环境切换后必须失效。
13. **键的改名与删除**：禁止直接删除正在使用的键。改名时保留旧键一个发布周期并加注释 `// @deprecated 将于 vX.Y.Z 移除，请改用 新键`，同时同步 `frontend_public.keys` 中的键名；删除前必须先确认后端与前端均无引用。
14. **改完必自检**：① `php -l backend/config/myconfig.php` 语法检查通过；② 确认 `config('myconfig.分组.键')` 能取到预期值；③ 确认 `GET /api/config` 返回键集与 `frontend_public.keys` 完全一致且不含私密项；④ 确认无代码仍在拼接硬编码地址。

## 二、正式环境可配置约定

1. **环境切换只改配置**：本地 / 预发 / 正式三套环境共用同一份代码，差异全部体现在 `deploy.env` 及其下游键上；禁止用 `if (env)` 分支写死 IP、端口、域名。
2. **接口侧地址**：`deploy.api.base_url` 为后端对外完整前缀（含 scheme、host、port），回调地址、生成绝对链接、定时任务拼接一律取该键；`deploy.api.timeout` 控制对外 HTTP 超时，缺省值需显式写出。
3. **前端侧地址**：`deploy.web.base_url` 为前端对外完整前缀。前端构建用的环境变量只能引用该值（由部署脚本或人工同步），不得在代码或构建脚本中写死生产 IP/端口。
4. **静态资源来源**：`deploy.resource.mode = local|cdn`。`local` 时资源走站点自身路径；`cdn` 时用 `deploy.resource.base_url` 作为根地址。切换 mode 不应改动任何业务代码。
5. **跨域**：`deploy.cors.allow_origin` 必须与 `deploy.web.base_url` 一致；正式环境禁止填写 `*`，多域名时用数组并逐个列明。
6. **图片资源来源**：公告图走 `announcement`，门户背景图走 `portal_theme`。代码拼接规则统一为「`upload_prefix` 或 `remote_base_url` + 数据库里存的相对路径」：本地文件用 `upload_prefix`，CDN/远程图床用 `remote_base_url`；禁止在模板或接口里写死 `/uploads/...` 或 `http://...` 全路径。
7. **skill 文件来源**：`skill.source = local|remote|api`。本地存在文件用 `local` + `local_path`；正式环境无本地文件时切 `remote`（拼 `remote_base_url`）或 `api`（请求 `api_endpoint`）；依赖方尚未就绪时置 `use_mock = true` 返回内置 mock 数据，保证页面不报错。
8. **缺文件降级**：任何读取本地文件（图片、skill、上传目录）的逻辑必须先判存在性；缺失时降级到远程地址或 mock，并记录一条带 traceId 的 warning 日志，禁止抛出未捕获异常导致接口 500。
9. **上传目录**：`upload.root` 指向当前环境真实存储目录，`upload.url_prefix` 与 `deploy.web.base_url` 同源或为已配置 CDN 前缀；`max_size`、`allowed_ext` 按正式环境要求设置，不在代码里二次写死限制。
10. **发布前环境差异核对清单**（逐项确认后再上线）：

    - `deploy.env` 是否为 `production`；
    - `deploy.api` 的 scheme/host/port/base_url/timeout 是否为正式值；
    - `deploy.web` 的 scheme/host/port/base_url 是否为正式域名/端口；
    - `deploy.resource.mode` 与 `base_url` 是 local 还是 cdn；
    - `deploy.cors.allow_origin` 是否等于 `deploy.web.base_url` 且不为 `*`；
    - `upload.root`、`upload.url_prefix`、`max_size`、`allowed_ext` 是否为正式值且目录可写；
    - `announcement` / `portal_theme` 的 `upload_prefix`、`remote_base_url` 是否与图片实际存放位置一致；
    - `skill.source` 及对应 `local_path` / `remote_base_url` / `api_endpoint` / `use_mock` 是否与正式环境文件情况匹配；
    - `jwt.secret`、`jwt.expire` 是否为正式值（且与 `.env` 一致）；
    - `database` 连接参数是否为正式库（主机、端口、库名、账号、前缀）；
    - `frontend_public.keys` 是否只含可公开项（`database`、`jwt` 绝不在内）。

11. **默认值也走配置**：门户等页面的默认分页、默认展示条数（`portal.page_size`）一律由前端从 `GET /api/config` 读取，前端不得写死 `10` / `20` 之类常量；新增默认值时同样写进 myconfig 并加白名单。
12. **数据库只存相对路径**：公告图、门户背景图在数据库中只保存相对路径（如 `announcement/2026/xx.jpg`），展示时再与 `upload_prefix` 或 `remote_base_url` 拼接；禁止把含域名/IP 的完整 URL 存库，否则环境迁移后图片必然失效。
13. **接口响应中的图片字段**：后端返回图片字段时统一返回可直接访问的完整 URL（前缀 + 相对路径），由 myconfig 决定前缀；前端不做二次拼接，避免两处逻辑不一致。

## 三、删除业务的磁盘回收约定（统一回收站）

1. **统一回收站原则**：任何业务实体（Skill、公告、门户背景图等）被删除（含软删除触发清理、硬删除）时，**不得直接 `unlink` / `rmdir` 删除其磁盘文件夹**；必须先把该实体对应的磁盘目录（如有）整体 `rename` 到统一回收站 `uploads/trash/{group}/`，由定时任务按保留期清理。保留期内误删可恢复，符合项目「缺失文件降级、禁止未捕获异常导致 500」的红线。
2. **回收站目录结构**：`uploads/trash/{group}/{label}_{时间戳}_{随机}/` 一个根目录、按业务分组。`group` 取值约定：`skill` / `announcement` / `portal`；`label` 取业务主键（如 Skill `id`、公告 `id`、门户模块名）。所有路径推导一律来自 `myconfig.trash.root`（缺省 `upload.root/trash`）与 `myconfig.trash.temp_dir`，禁止硬编码。
3. **原子性与同分区约束**：移入回收站必须是单次目录级 `rename()`，同文件系统内为原子操作（O(1)，无「删一半」中间态）。**回收站根目录与正式资源目录必须位于同一文件系统**，否则 `rename()` 退化为「复制 + 删除」、失去原子性；生产部署脚本须用 `df -P` 校验两者 Filesystem 一致，并让 `www-data` 对两目录均可写。
4. **文件操作在事务外**：删除接口的数据库操作（含软删除打标）在 `Db::transaction` 内完成；文件移入回收站必须在**事务提交之后**执行。若把文件移动放进事务，一旦回滚则磁盘已不可恢复。文件操作失败只记 warning 日志、不阻断接口（DB 已成功则仍返回成功）。
5. **回收站配置项（myconfig.trash）**：保留期 `retention_days`（超期目录由 GC 彻底删除）、暂存目录名 `temp_dir`（位于各资源主目录下，解析未提交前先落此处）、暂存保留时长 `temp_retention_hours`。所有取值集中在 `myconfig.trash`，业务代码不得写死。
6. **GC 定时清理**：提供 `skill:gc` 命令（支持 `--dry-run`），清理超期回收站目录与超期暂存文件，需配每日 cron；失效文件只移回收站、不直接删，避免不可逆。
7. **实现出口收敛**：文件生命周期操作（暂存、归位、移回收站、GC）统一收敛到 `app/service/SkillStorage.php` 与控制器编排；新增资源的删除回收须复用同一套 `common.php` 的 `move_to_trash()` / `trash_root()` / `trash_group_dir()` 辅助函数，不得各写一套 `unlink` / `rename` 逻辑。
8. **历史数据迁移幂等**：涉及目录重构时（如 Skill 由平铺改「一实体一目录」），提供一次性 `skill:migrate-packages` 类幂等命令，无对应记录的孤儿文件只移回收站、不直接删，可重复执行。

## 四、发布检查流程（AI 每次必执行的 7 步）

1. **列变更**：读取 `git status` / `git diff --stat`（只读，不执行任何写操作），列出本次新增、修改、删除的全部文件。
2. **分类**：把变更文件归为「业务代码 / 配置（myconfig）/ 数据库迁移 / SQL 脚本 / 文档 / 静态资源」六类，分别计数。
3. **排除项校验**：确认以下文件**不在**上传列表中——`backend/.env`、`backend/runtime/`、`backend/vendor/`、`frontend/node_modules/`、`frontend/dist/`、`*.log`、`composer.lock`。若它们出现在变更里，标记为「禁止上传」并提示补齐 `.gitignore` 或 `git rm --cached`。
4. **数据库增量脚本判定**：只要表结构或数据有变，必须**双份交付**——
   - 迁移文件：`backend/database/migrations/YYYYMMDDHHmmss_{简述}.php`（think-migration）；
   - 增量脚本：`docs/sql/YYYYMMDDHHmmss_{简述}.up.sql` 与同名 `.down.sql`，头部注释与命名遵循 `docs/sql/README.md`（基线为已有 4 个迁移，不补写历史 SQL）。
   清单中写明脚本文件名、执行顺序（up 按时间戳升序，回滚按降序）与是否需要备份。
5. **myconfig 变更单独成节**：若 `backend/config/myconfig.php` 有改动，单独一节输出，格式为「变更键 → 旧值 → 新值 → 影响范围」，并在节首标注「⚠️ 含生产配置，需用户确认后方可上传」。**未获得用户明确确认前，不得 `git add` / `commit` / `push` 该文件，也不得把其内容写入任何待上传产物或文档**；同时按第二部分第 10 条核对环境差异。
6. **输出清单**：给出三张列表——① 需上传的文件清单（按第 2 步分类）；② 需按序执行的 SQL 脚本；③ 需在生产手工处理项（如同步 `backend/.env`、创建/授权上传目录、切换 `skill.source`、重启服务）。
7. **不自动提交**：全流程只输出清单与建议命令，**不自动执行 `git add` / `git commit` / `git push`**；由用户确认后自行执行，或在用户明确逐次授权后再执行。

### 清单输出模板（第 6 步按此格式输出）

```
一、需上传的文件
  1) [代码] backend/app/.../Xxx.php        （新增/修改，说明一句话）
  2) [文档] docs/...md

二、需执行的 SQL（按序）
  1) docs/sql/20260920000100_xxx.up.sql   （回滚：同名 .down.sql，回滚时按时间戳降序）
  ※ 执行前需备份表：inue_xxx

三、生产手工项
  1) 同步 backend/.env 的 DB_* / JWT_SECRET
  2) 创建并授权 upload.root 目录

四、⚠️ myconfig 变更（需确认后方可上传）
  - deploy.web.base_url：旧值 A → 新值 B（影响：分享链接、CORS）
  - 是否允许上传 backend/config/myconfig.php？请回复「允许/不允许」。
```

若本次无 myconfig 变更，第四节写「本次 myconfig.php 无变更，无需确认」；若无 SQL 变更，第二节写「本次无增量脚本」。

## 例外条件

1. 除非单次需求另有明确说明，否则一律按上述标准执行；不得以「只是小改动」为由跳过第 5 步的确认。
2. `myconfig.php` 的上传确认**不可被一次性授权覆盖**：每次发布只要该文件有变更，都必须重新确认。
3. 紧急 hotfix 同样需走完 7 步，但允许用户在确认清单后要求「其余文件先提交、myconfig 暂不提交」，此时必须明确写出哪些文件被排除在本批之外。
