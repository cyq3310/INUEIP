# 操作日志留存规范（inue_operation_log）

## 背景
`inue_operation_log` 记录所有后台写操作（经 `write_oplog()`，见 `backend/app/common.php`），随使用时间持续增长。
若长期不治理，单表查询会越来越慢。本规范约定其存储与清理方式。

## 策略：按月 RANGE 分区 + 保留 180 天
- **按月分区**：`PARTITION BY RANGE (TO_DAYS(created_at))`，每月一个分区，命名 `pYYYYMM`（如 `p202609`）。
- **`created_at` 仍是完整 datetime**（精确到秒），不做任何裁剪；分区只是按月份决定数据落在哪个物理分区。
- **保留 180 天**：整月都早于保留期的分区由维护命令 `DROP PARTITION` 秒级移除，不做大批量 `DELETE`（避免扫表与碎片）。

## 为什么主键是 `(id, created_at)`
MySQL/MariaDB 要求：**分区字段必须出现在所有唯一键中**。原主键是单独的 `id`，不满足约束，
因此迁移 `20260928000100_partition_operation_log.php` 将主键调整为 `(id, created_at)`，
同时把 `created_at` 改为 `NOT NULL`（NULL 会落入首个分区），并新增索引 `idx_oplog_created`。

> 写入侧 `write_oplog()` 与 `OperationLog` 模型**无需任何改动**，模型固定指向 `operation_log`。

## 分区兜底：pmax
迁移会额外创建 `pmax VALUES LESS THAN MAXVALUE` 兜底分区。
即使维护任务漏跑，跨月时新数据也能落进去，**不会导致 `write_oplog` 写入失败**。
新增月份分区时通过 `REORGANIZE PARTITION pmax INTO (...)` 拆分出来。

## 每月运维
命令：`php think oplog:maintain`（PHP 用 `h:\XAMPP\php\php.exe`；默认补建未来 6 个月、保留 180 天）。

- 演练（不改库）：`php think oplog:maintain --dry-run`
- 自定义：`--months=12`（预建月数）、`--days=365`（保留天数）
- 幂等：重复执行不会产生重复分区，已存在月份自动跳过。

建议**每月 1 号**执行一次。

**Windows（任务计划程序）**
```
程序/脚本：h:\XAMPP\php\php.exe
参数：think oplog:maintain
起始位置：h:\XAMPP\htdocs\INUEIP\backend
```

**Linux（crontab，每月 1 号 03:10）**
```
10 3 1 * * cd /path/to/INUEIP/backend && /usr/bin/php think oplog:maintain >> /var/log/inueip-oplog-maintain.log 2>&1
```

**部署到正式环境是否需要重设？**
- **不需要重设的部分**：迁移（`20260928000100`）与 `oplog:maintain` 命令都属于代码，随发版自动生效，正式库执行 `php think migrate:run` 后即完成分区。
- **需要单独配一次的部分**：**操作系统的定时任务是环境级配置，不会随代码部署带过去**。因此在正式服务器上需要按上面的方式创建一次计划任务/定时任务；**配好后长期有效，后续发版无需再配**（除非迁移服务器或更换 PHP 路径）。
- 正式环境的 PHP 可执行文件路径与工作目录需按实际环境替换。
- 上生产前建议先跑 `php think oplog:maintain --dry-run` 确认输出符合预期。

> 漏跑不会丢数据（有 pmax 兜底），但会让当月数据堆积在同一个分区里，建议配合监控提醒。

## 字段说明（可读性）
| 字段 | 说明 |
| --- | --- |
| `user_id` | 操作人用户 ID，**保留**（用于程序关联与按用户筛选，`idx_oplog_user_created` 仍依赖它） |
| `username` | 操作人账号（冗余列，仅提升直接查表时的可读性） |
| `action` / `detail` / `ip` / `created_at` | 动作、详情、来源 IP、时间 |

- 常规接口（走 `AuthCheck`）：`write_oplog()` 自动从 `request->userProfile['username']` 取账号，**调用方无需改动**。
- **登录接口无登录态**（`user_id=0`），必须显式传第三个参数：`write_oplog('auth.login', "...", $username)`。
  其他无登录态的新接口同理，否则 `username` 会为空。
- 历史登录记录（本次改造前写入）的 `username` 为空，其账号信息在 `detail` 中；**新记录起均已填充**。

## 查询注意事项（重要）
- **要让分区裁剪生效，时间条件请写字面量**：
  `WHERE created_at >= '2026-09-01' AND created_at < '2026-10-01'` → 只扫 `p202609`。
- 实测 `WHERE created_at >= CURDATE()` **无法裁剪**，会扫全部分区（MySQL 对该类函数不支持分区裁剪）。
  用 UI 或脚本查日志时，请在代码里先把日期算好再拼进 SQL。
- 现有索引：`PRIMARY KEY (id, created_at)`、`idx_oplog_user_created (user_id, created_at)`、`idx_oplog_created (created_at)`。
  按时间倒序翻页请用 `idx_oplog_created`；`idx_oplog_user_created` 服务于「指定用户 + 时间范围」的查询。

## 以后若要加日志查看页面
按时间范围查询即可由数据库自动跨月裁剪，**不需要 UNION 多张表**；
若使用MySQL分区方案的同时也想做归档导出，可配合定期 `mysqldump` 单分区数据留档。

## 禁止事项
- 不要把 `inue_operation_log` 改成按月独立表轮转的方案（跨月查询需多表 UNION，且 TRUNCATE 后自增 id 会跨月重复）。
- 不要手工 `DELETE FROM inue_operation_log WHERE created_at < ...` 清历史，交给 `oplog:maintain` 用 DROP PARTITION。
- 不要改动 `pYYYYMM` 命名规则与 `pmax` 兜底分区，维护命令依赖该约定识别月份与执行清理。
